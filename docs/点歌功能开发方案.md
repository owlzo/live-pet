## 0. 结论摘要

1. **技术链路可行**：`orpheus://<base64 JSON>` 协议能精确点播指定歌曲，冷启动与热启动均实测通过，且不需要 CDP、不需要重启客户端。
2. **「搜歌」必须绕开客户端**：协议是单向投递、没有返回值，搜歌要走 HTTP 搜索接口拿 `songId`。所以准确表述是「**接口搜歌 + 客户端播放**」，不是「客户端搜歌并播放」。
3. **最高风险不是技术，是版权**：网易云的曲库状态 ≠ 抖音的授权状态。工程上只能做到「白名单优先 + 黑名单兜底 + 默认拒绝 + 人工复核」，**不能承诺自动合规**。功能默认关闭，开启前必须过免责确认。

## 1. 需求描述

### 1.1 背景

桌宠已在抖音直播间承担「读弹幕 / 谢礼物 / 播动画 / 语音」的互动角色。点歌是把互动从「说话」扩展到「内容」的自然延伸：观众用弹幕点歌，直播间按队列播放，桌宠负责报幕与秩序管理。

### 1.2 目标与非目标

**目标**

- 观众在弹幕里用固定前缀点歌，系统搜到具体曲目后入队，按顺序在直播间播放。
- 主播在控制台能看到队列、删歌、切歌、暂停接单，并对高风险曲目一票否决。
- 全链路默认关闭，开启时明确告知版权风险。

**非目标（本期不做）**

- 不做在线曲库的批量下载、转码、缓存到本地。
- 不做自动版权判定（技术上不可行，详见 §2.6）。
- 不做礼物点歌的竞价排序（P2，预留字段）。
- 不支持除网易云以外的音源。

### 1.3 角色与场景

| 角色 | 场景 | 关键诉求 |
| --- | --- | --- |
| 观众 | 弹幕 `点歌 蓝莲花` | 立刻得到「收到 / 没找到 / 已排第 N 位」的明确反馈 |
| 主播 | 开播中盯着控制台 | 队列可控、可删、可切，不被烂歌拖住 |
| 主播 | 收到平台静音警告 | 一键停单、清理队列、把风险曲目拉黑 |
| 运营 | 复盘 | 谁点了什么、什么时候播的、为什么被拒 |

### 1.4 功能清单

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| P0 | 弹幕点歌 | 前缀可配（`点歌/点播/来一首`），支持全角空格、大小写、去标点 |
| P0 | 搜歌与候选消歧 | 取 Top3 候选；歌名完全匹配优先，其次按热度；歧义时按第一首并播报歌名 |
| P0 | 规则网关 | 白名单 / 黑名单 / 敏感词 / 时长上限 / 频次，全部前置在入队之前 |
| P0 | 队列 | FIFO、上限、每人冷却与配额、同曲 30 分钟去重 |
| P0 | 播放与观测 | 投递命令 → 校验是否真的在播 → 按 duration 推进 → 超时降级 |
| P0 | 播报 | 桌宠 TTS 报幕（"接下来播放 A 点的《X》"），先报幕再投歌 |
| P0 | 控制台 | 新页签：队列、搜索、试听、删/切/暂停、黑名单维护、开关与免责确认 |
| P1 | 风险分级展示 | 每条请求标注 `allowed / review / blocked` 与依据 |
| P1 | 历史与统计 | 点歌记录、被拒原因分布 |
| P1 | 礼物加急 | 礼物事件插入队首（复用现有 `gift` 事件） |
| P2 | 多音源 | 抽象 `SongProvider`，预留第二实现 |
| 不做 | 自动版权判定 | 见 §2.6 |

### 1.5 非功能需求

| 维度 | 指标 |
| --- | --- |
| 响应 | 点歌到播报 ≤ 2.5s（不含排队）；投递命令开销 ≤ 100ms |
| 可靠性 | 客户端重启、网络抖动后队列不丢、不重复播 |
| 可观测 | 每次状态迁移写一行结构化日志（requestId / songId / 阶段 / 耗时 / 结果） |
| 安全 | 只允许本机触发；`songId` 必须纯数字；`orpheus://` 只由宿主进程发起 |
| 合规 | 默认关闭；开启需一次显式确认；所有拦截留痕 |

### 1.6 术语

- **投递**：通过 `orpheus://` 协议把播放命令交给网易云客户端，单向、无返回。
- **观测**：从客户端外部推断"到底播没播、播到哪"，本方案唯一手段是窗口标题 + 时长推算。
- **规则网关（Guard）**：入队前的同步判定，决定 `allow / review / block`。

## 2. 规则约束：抖音直播的版权与内容边界

> 本节结论用于**产品设计取舍**，不构成法律意见。上线前建议由法务或平台运营复核。

### 2.1 三层规则体系

| 层级 | 依据 | 对产品的约束 |
| --- | --- | --- |
| 法律层 | 《著作权法》：音乐作品含词、曲、表演者、录音制品四类权利主体；直播场景主要落入**广播权**（背景播放）与**信息网络传播权**（回看），2020 年修法后录音制品另有**获酬权** | 未经授权播放即可能侵权，与是否收费、是否盈利无必然关系；"网上能免费听"不构成抗辩 |
| 平台层 | 抖音《直播行为规范》《社区自律公约》与直播伴侣内置曲库（炙热星河等） | 平台只对**自有授权曲库**提供使用许可；曲库外音乐由主播自行承担授权责任 |
| 处罚层 | 平台侧：静音（音频被切断/替换）→ 断流/中断直播 → 限流、扣信用分 → 封禁直播权限；权利侧：警告函、批量取证起诉 | 头部曲目维权已批量化，单曲判赔常见数千元量级 |

**关键事实**：抖音内置曲库的音乐，主播在直播间使用一般无版权风险；而「主播自行选用曲库外的歌」属于自担风险行为。我们的点歌功能天然属于后者——这是本需求最大的结构性风险，必须在产品层面明确告知，不能靠技术掩盖。

### 2.2 直播用乐涉及的权利

| 使用形态 | 涉及权利 | 说明 |
| --- | --- | --- |
| 背景播放原曲（本方案） | 词曲广播权 + 录音制品获酬权（+ 回看时的信网权） | 不涉及表演者现场直播权 |
| 主播跟唱 | 词曲表演权/广播权 + 表演者权 | 风险更高，本方案不提供"跟唱模式" |
| 播放 MV / 影视片段 | 视听作品著作权 | 明确禁止，直接进黑名单 |

### 2.3 可播性判定标准（四级）

| 等级 | 判定依据 | 处理 |
| --- | --- | --- |
| **L0 允许** | ① 抖音官方曲库曲目；② 已取得书面授权的曲目（保留授权文件）；③ 公有领域作品；④ 主播自有版权 | 直接放行 |
| **L1 待复核** | 有明确商用授权线索但未归档（如独立音乐人公开声明可商用、CC 协议） | 入队但标记 `review`，控制台高亮，主播可一键否决 |
| **L2 拒绝** | ① 曲库外热门流行曲；② 影视/游戏 OST；③ 竞品平台独家；④ 曾被投诉或已被平台静音的曲目；⑤ 艺人级黑名单命中 | 直接拒绝并告知观众原因类别 |
| **L3 未知** | 无法判定版权状态（绝大多数情况） | **默认拒绝**（fail-closed），提示主播"需人工确认后可放行" |

> 默认策略是 `fail-closed`。若主播把模式切换为 `fail-open`（默认拒绝改为默认放行），控制台必须持续显示风险横幅，且该选择写入审计日志。

### 2.4 内容安全红线（与版权正交，必须同时过滤）

命中任一项即拒绝，且不进队列：

| 类别 | 示例判定 |
| --- | --- |
| 政治敏感 | 涉政人物、事件、调侃时政的曲目与歌词 |
| 色情低俗 | 歌名/歌词含性暗示、擦边表述 |
| 暴力恐怖 | 宣扬暴力、自残、恐怖主义 |
| 民族宗教 | 涉及宗教音乐、民族争议内容 |
| 违禁品与违法 | 涉毒、赌博、诈骗、翻墙等 |
| 未成年人保护 | 涉未成年人不良导向 |
| 迷信 | 招魂、算命、法事类音效 |
| 广告导流 | 歌名夹带联系方式、二维码、站外链接 |

实现上分两层：**元数据层**（歌名/艺人/专辑做敏感词匹配，快、可解释）+ **黑名单层**（人工维护的曲目/艺人清单）。

### 2.5 过滤机制（工程落地）

```
弹幕 → 指令解析 → 搜索(Top3) → ①敏感词 ②艺人/曲目黑名单 ③白名单 ④时长 ⑤频次
     → 判定(allow/review/block) → 入队 → 投递前二次校验(防黑名单中途更新) → 播放
```

| 机制 | 位置 | 说明 |
| --- | --- | --- |
| 敏感词表 | ① | 内置基础词表 + 控制台可编辑，命中即 `block`，记录命中词 |
| 曲目/艺人黑名单 | ② | 支持精确 `songId`、艺人名、歌名包含匹配 |
| 平台曲库白名单 | ③ | 人工导入（曲库导出/手工维护），命中即 `allow` 并跳过后续风险判定 |
| 单曲时长上限 | ④ | 默认 240s，超时强制切歌（降低"整首完整播放"的侵权暴露面，也是直播节奏需要） |
| 频次控制 | ⑤ | 同曲 30 分钟不重复；单人 5 分钟冷却、每小时 3 首 |
| 投递前复核 | 末段 | 防止"排队期间主播刚把这首歌拉黑" |
| 审计 | 全程 | 每条请求记录判定等级、依据、命中的规则 ID |

### 2.6 关于「自动合规」的边界声明（重要）

**技术上无法自动判定一首歌能否在抖音直播中播放。** 原因：

1. 网易云的"可播放"只代表其平台授权，与抖音的直播授权完全独立；
2. 抖音曲库没有公开、稳定的机器可读接口；
3. 版权状态随时变化（下架、独家、维权名单更新）。

因此产品的定位是：**风险收敛工具，不是合规保证**。UI 文案与文档都必须避免"已自动规避版权风险"这类表述。

### 2.7 授权与成本参考

| 路径 | 适用 | 说明 |
| --- | --- | --- |
| 抖音官方曲库 | 通用 | 成本最低、风险最低，应作为主推路径 |
| 音著协 / 音集协一揽子许可 | 有稳定开播需求的账号 | 词曲与录音制品分别授权 |
| 直接联系版权方 | 特定曲目 | 保留书面授权备查 |

> 音集协曾公布《网络直播使用音乐录音制品版权费标准（草案）》：泛娱乐直播（不含 K 歌）约 100 元/直播间/年、含 K 歌约 300 元/直播间/年、电商直播间约 10000 元/直播间/年。**该数字为草案口径，仅作成本量级参考，不作报价依据。**

## 3. 技术方案：网易云客户端后台播放

### 3.1 总体架构

```
弹幕 ──▶ 指令解析 ──▶ 搜索(HTTP) ──▶ 规则网关 ──▶ 点歌队列 ──▶ 调度器
                                                              │
                                          ① TTS 报幕（桌宠，先）│
                                          ② orpheus 投递（后）  ▼
                                                    网易云桌面客户端
                                                              │
                                          ③ 观测器（窗口标题/时长）
                                                              │
                                                    状态机推进 / 失败降级
```

**与上一版方案的差异**：播放由外部客户端完成，音频不经过我们的渲染端，因此**不需要新增 state 叶子、不需要改 runtime**，`voice` 与歌曲也不会互抢音频通道（代价是失去播放回执，见 §3.6）。

### 3.2 搜歌链路

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **S1 公开搜索接口** | `GET https://music.163.com/api/search/get?s=<kw>&type=1&limit=3`（带 `Referer`） | 无需登录、返回 id/歌名/艺人/**duration**、实测可用 | 非官方契约，可能加签/限流 | **默认** |
| S2 登录态接口 | 读客户端 CEF cookie（`MUSIC_U`）后调 weapi | 结果更全、抗风控 | 需解 sqlite/加密、涉及凭据安全 | P2 备选 |
| S3 CDP 驱动客户端搜索 | 带 `--remote-debugging-port` 注入 JS 读搜索结果 | 与客户端一致 | **本机实测客户端 15~30s 内自行退出**，不稳定 | 不采用 |
| S4 本地曲库/别名表 | 预置 `歌名 → songId` 映射 | 稳定、零网络 | 覆盖有限 | **兜底** |

实现要点：搜索超时 3s、失败重试 1 次、结果缓存 10 分钟；`duration` 直接用于队列计时。

### 3.3 播放链路（实测结论）

**桌面端的正确格式是 base64 命令载荷**，不是移动端的 `orpheus://song/{id}`：

```
orpheus://eyJ0eXBlIjoic29uZyIsImlkIjoiMTY4MDkxIiwiY21kIjoicGxheSIsImNoYW5uZWwiOiJ3ZWJzZXQifQ==
         └─ base64({"type":"song","id":"168091","cmd":"play","channel":"webset"})
```

| # | 验证项（Windows 11 / v3.1.34 / 安装于 `D:\网易云`） | 结果 |
| --- | --- | --- |
| 1 | 协议注册：`HKLM\SOFTWARE\Classes\orpheus\shell\open\command` = `cloudmusic.exe --webcmd="%1"` | ✅ |
| 2 | 冷启动（客户端未运行）+ base64 载荷 | 直接开播目标曲目 ✅ |
| 3 | 热启动（客户端运行中）+ 同一载荷 | 切歌成功 ✅ |
| 4 | `orpheus://song/186016`（移动端格式） | 只唤起，不切歌 ❌ |
| 5 | 无效 songId | 静默无反应，无报错 ⚠️ |
| 6 | 版权受限曲目（如网易云无授权的热门曲） | 同样静默失败 ⚠️ |
| 7 | 最小化启动（`-WindowStyle Minimized` + `--webcmd`） | 播放正常启动 ✅ |

**投递方式（Electron 主进程）**

```ts
// 优先用系统协议打开器，不直接拉起 exe
shell.openExternal(`orpheus://${Buffer.from(JSON.stringify({
  type: 'song', id: songId, cmd: 'play', channel: 'webset',
})).toString('base64')}`);
```

**注意事项**

- `songId` 必须做 `/^\d{1,20}$/` 校验后再拼接，禁止把外部字符串直接塞进 payload。
- 两次投递间隔 ≥ 400ms，避免客户端丢命令。
- 不允许把 `orpheus://` 暴露给浏览器页面或直播间观众（否则任意网页都能唤起用户客户端）。

### 3.4 「不弹界面」的实现选型

> 目标：点歌时不把网易云窗口弹到前台。**"最小化"不等于"不弹"，需要分层处理。**

| 方案 | 做法 | 可见性 | 复杂度 | 稳定性 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A 常驻最小化** | 桌宠启动时确保客户端在跑（最小化启动），此后只投递命令 | 托盘/任务栏可见，不抢焦点 | 低 | 高 | **默认** |
| **B 投递后最小化** | 每次投递后调 `ShowWindow(hwnd, SW_MINIMIZE)` | 有短暂闪现 | 中 | 中 | A 失效时兜底 |
| **C 独立虚拟桌面** | `CreateDesktop` + `CreateProcess(lpDesktop)` 在隐藏桌面启动客户端 | 完全不可见 | 高 | 待验证 | V2 增强，需 PoC |
| **D 自建播放器** | 接口取流后由本地播放器播 | 无客户端 | 高 | 低（VIP/加密/合规） | **不推荐** |
| **E 引导用户设置** | 让用户在客户端里勾选「关闭主窗口时最小化到托盘」 | 托盘图标 | 零 | 高 | 与 A 配套 |

**推荐组合：E + A 起步，B 兜底。**

流程：

1. 桌宠启动 → 探测 `cloudmusic.exe` 是否在运行（注册表读路径，不能硬编码盘符）。
2. 未运行 → 以最小化方式预启动（不投递命令，避免突然出声）；用户可在配置里关闭"自动拉起"。
3. 点歌命中 → 直接投递，客户端已在后台，不产生新的窗口。
4. 若检测到窗口被前置（可选：投递前后对比前台窗口标题）→ 执行 B 的最小化兜底。

**未验证项（需在联调阶段补测）**：

- 客户端已在后台运行时，收到 `--webcmd` 是否会把窗口前置（Windows 焦点策略 + 客户端自身实现决定）；
- 关闭主窗口到托盘后，播放与投递是否仍正常；
- 方案 C 在隐藏桌面下的渲染/音频是否正常。

### 3.5 交互流程（时序）

```
观众        桌宠宿主                      网易云客户端            控制台
 │  点歌 X     │                              │                    │
 ├────────────▶│ 解析指令                      │                    │
 │             │ 搜索(≤3s) → Top3             │                    │
 │             │ Guard 判定                    │                    │
 │             │ ├ block → 播报"不能播"        │                    │
 │             │ └ allow → 入队                │                    │
 │◀─播报"排第N位"┤                              │                    │
 │             │                              │                    │
 │        （轮到该曲）                          │                    │
 │             │ ① TTS 报幕（2.5s）            │                    │
 │             │ ② 投递 orpheus ──────────────▶│ 开始播放            │
 │             │ ③ 3s 后校验标题 ─────────────▶│                    │
 │             │    ├ 命中 → 计时(duration)     │                    │
 │             │    └ 未命中 → 重投1次 → 降级   │                    │
 │             │ ④ duration 到点 / 标题变化     │                    │
 │             │    → 下一首                     │                    │
 │             │ ⑤ 全量状态写 /song/status ────────────────────────▶│
```

**为什么先报幕再投歌**：桌宠 TTS 与客户端播放是两条独立音频通道，同时出声会糊在一起。先念完（或固定 2.5s）再投递，听感上是"报幕 → 起歌"。

### 3.6 状态观测与队列推进

协议是**单向**的：没有"播放成功/失败/结束"的回执。状态机只能靠外部信号拼：

| 信号 | 获取方式 | 用途 | 可靠度 |
| --- | --- | --- | --- |
| 窗口标题（`歌名 - 歌手`） | `tasklist /v /fi "imagename eq cloudmusic.exe" /fo csv`，5s 一次 | 校验是否切到目标曲、发现提前切歌 | 中（歌名含 ` - ` 会误解析；页面标题可能覆盖） |
| 曲目时长 | 搜索接口返回的 `duration` | 队列推进的主时钟 | 高（±1s） |
| 进程存活 | 进程探测 | 客户端崩了要暂停队列 | 高 |
| SMTC（系统媒体会话） | WinRT，需原生模块 | 精确播放状态 | 高，但引入原生依赖 → P1 可选 |

**状态机**

```
idle ──投递──▶ requesting ──3s内标题命中──▶ playing ──duration到点/标题变化──▶ ended
                    │                                  │
                    └──超时/未命中──▶ retrying ──仍失败──▶ failed（跳过，播报"这首歌放不了"）
```

**边界处理**

- 主播手动暂停/切歌 → 下一拍标题变化即被识别为 `ended`，队列继续；不追责、不重投。
- 客户端退出 → `process-alive` 为假，暂停队列并提示，恢复后从队首继续（不跳过）。
- 系统休眠/唤醒 → 计时器基于 `Date.now()` 与目标结束时刻比较，不用 `setTimeout` 累加，避免漂移。

### 3.7 失败识别与降级

| 失败类型 | 识别方式 | 用户可见反馈 | 处置 |
| --- | --- | --- | --- |
| 搜不到 | 搜索结果空 | 播报"没找到《X》，换个名字试试" | 结束 |
| 被规则拦截 | Guard 返回 block | 播报"这首不能播哦"（不暴露具体规则） | 结束 |
| 投递无效 | 3s 标题未变 | 播报"这首放不了，跳过" | 重投 1 次后跳过 |
| 曲目无版权/VIP | 同"投递无效"（客户端静默） | 同上 | 标记该 id 冷却 24h，避免反复点同一首 |
| 客户端未启动 | 进程探测 | 播报"播放器没开，稍等" | 自动拉起一次，失败则暂停接单 |
| 平台静音 | **无法自动感知** | 无 | 由主播人工发现，提供"一键停单"按钮 |

## 4. 风险清单

| 级别 | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| **P0** | 直播播放未授权音乐被平台静音/断流 | 直播事故、限流、封禁、民事赔偿 | 默认关闭；白名单优先 + fail-closed；默认单曲 ≤240s；免责确认；提供一键停单 |
| **P0** | 协议与搜索接口均为非公开契约，客户端升级即失效 | 功能整体不可用 | 版本探测 + 能力开关；格式化配置化（payload/字段集中一处）；降级提示而非崩溃 |
| **P0** | 静默失败（无版权/无效 id）无法与"正常播放"区分 | 队列卡住或空白 | 3s 标题校验 + 重投 1 次 + 标记冷却 + 明确播报 |
| **P1** | 客户端未登录，大量曲目不可播 | 点歌成功率低 | 状态面板显示"登录/未登录"，引导登录；失败率过高时提示 |
| **P1** | 窗口抢焦点（"不弹界面"未完全验证） | 打断主播操作 | 优先常驻后台；投递后最小化兜底；V2 上隐藏桌面 |
| **P1** | 主播手动切歌/暂停导致失同步 | 队列节奏错乱 | 标题轮询识别变化即视为 ended；提供"重新对齐"按钮 |
| **P1** | 安装路径差异（本机在 `D:\网易云`） | 无法拉起客户端 | 只从注册表读 `orpheus` 命令解析 exe 路径；配置可覆盖 |
| **P1** | 标题解析脆弱（歌名含 ` - `、页面标题覆盖） | 误判播完/误判失败 | 解析取最后一个 ` - ` 分段；失败只降级不阻断；SMTC 作为 P1 增强 |
| **P2** | 投递频率过高被客户端丢弃 | 偶发不播 | ≥400ms 间隔 + 重投 |
| **P2** | 音频输出设备/音量不受控 | 直播混音失衡 | 文档说明；建议主播用系统混音或直播伴侣调音量 |
| **P2** | 桌宠 TTS 与歌曲重叠 | 听感糊 | 先报幕后投歌；TTS 期间不投递 |
